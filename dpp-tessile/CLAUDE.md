# DPP Tessile — правила проекта

Многоязычная SaaS-платформа для создания и ведения цифровых паспортов текстильной продукции (ESPR DPP). Это не генератор QR и не лендинг.

## Как работать
- Сначала изучи репозиторий (стек, структуру, БД, текущие функции). Потом краткий план с зависимостями. Потом код.
- Работаем по одной задаче за раз. Бери только ту задачу, которую дал пользователь. Не забегай вперёд.
- Не удаляй работающий функционал и данные. Не переписывай проект с нуля, если архитектуру можно безопасно развивать.
- Необратимые миграции и смена стека: сначала объясни риски и безопасный план, дождись согласования.
- Реализуй изменения в коде, а не только описания.
- Никаких кнопок без рабочего действия и демоданных вместо реальной функциональности. Нереализованное показывай честным пустым состоянием («Раздел в разработке»).
- Внешняя интеграция без ключа: сделай реализацию, конфиг и инструкцию. Не имитируй успешное подключение. Неуспешный внешний запрос не показывай как успех.
- После каждой задачи запусти сборку, линтер и тесты, исправь ошибки, задокументируй ограничения. Не подменяй результаты тестов предположениями.
- В конце каждой задачи дай: изменённые файлы, реализованное, результаты проверок, ограничения, следующий шаг.

## Принципы продукта
- Пользователь вводит данные один раз, система помогает их проверить и переиспользует.
- Автоматизация и ИИ не заменяют человека: ИИ не утверждает, не подписывает и не публикует паспорт.
- Состав, происхождение и соответствие нельзя объявлять подтверждёнными по ручному вводу, заявлению поставщика или факту, что ИИ прочитал документ.
- Индекс готовности не означает соответствие законодательству.
- В паспорт попадает только то, что требует закон. Данные из документов не добавляются в паспорт автоматически.
- Статус «подтверждено в блокчейне» только после подтверждённой транзакции и проверенного доказательства. До этого помечай как тестовое.
- Не придумывай законодательные требования и сертификаты. Различай действующие нормы и проекты.

## Дизайн и UX

- В любой момент понятно: где я, с чем работаю, что готово, что требует внимания, что делать дальше.
- Подсказки у полей, поиск, черновики, предупреждение о несохранённых изменениях, подтверждение опасных действий, пустые состояния с объяснением.

- Единые таблицы, формы, диалоги. Не перегружай анимациями и всплывающими окнами.

## Безопасность
- Изоляция организаций, Row Level Security, серверная авторизация каждого действия и каждого документа.
- Защита от IDOR, CSRF, XSS. Валидация ввода, ограничение частоты чувствительных запросов, безопасные сессии.
- Загрузки: проверка MIME, размера, безопасная обработка архивов, запрет исполнения. Скачивание только по правам.
- Секреты только в переменных окружения, описание в `.env.example`, без реальных значений. Публичная страница не использует привилегированные ключи.
- Журнал аудита для административных и значимых действий.
- ИИ: не передавай внешней модели персональные данные, пароли, ключи, платёжные данные и закрытые коммерческие документы без разрешённого основания. Минимизируй данные.
- Поставщик видит только разрешённое ему. Публичная страница не раскрывает внутренние комментарии, персональные данные сотрудников и закрытые документы.

## Роли
Владелец организации, администратор, сотрудник, ответственный за составление паспорта, специалист по документам, ответственный за утверждение, поставщик, аудитор с ограниченным доступом. Список расширяется через систему разрешений. Права на чтение, редактирование, утверждение и публикацию раздельные.

## Данные
- Стек: развивать существующий. Supabase/PostgreSQL использовать, только если решение согласовано после аудита.
- Нормализованная схема, внешние ключи, ограничения, индексы, транзакции, версионируемые миграции, мягкое удаление где нужно.
- JSONB только для гибких структур. Ключевые сущности и связи реляционные.
- Сохраняй исходный текст производителя и происхождение значений (источник, дата, кто подтвердил). Переводом оригинал не перезаписывай.

## Публичный паспорт и PDF
- Публичный паспорт это веб-страница по стабильному адресу платформы. QR ведёт на адрес, а не содержит данные. Показывается актуальная утверждённая версия. Снятый с публикации паспорт показывает статус, а не подменяется другой версией.
- PDF только внутренний (A4, номера страниц, дата и версия, отметка «ВНУТРЕННИЙ ДОКУМЕНТ», проверка прав). Формируется из структурированных данных, не скриншотом. Кнопка «Скачать PDF» на публичной Trust Page разрешена владельцем (2026-10-26) для LITE и выше, но это отдельный публичный шаблон только с публичными полями, не внутренний PDF.

## Языки
Ровно 12: EN, IT, DE, FR, ES, PT, PL, RO, TR, UK, RU, NL. Другие не добавлять.
Пока идёт разработка: все пользовательские строки через i18n-ключи (`t("ключ")`), рабочий словарь RU, fallback на EN, никаких захардкоженных строк. `npm run i18n:check` падает, если ключа нет в ru.js. Остальные переводы делаются отдельной последней задачей.
Язык интерфейса, язык исходного документа и язык публичного паспорта независимы.

- Не ставь зависимости без необходимости. Бизнес-логику не дублируй в компонентах.

- Общие компоненты: таблицы, фильтры, поиск, карточки, статусы, формы с подсказками, диалоги подтверждения, уведомления, шаги мастера, индикаторы загрузки, пустые состояния.

## Бэкапы и восстановление
Бэкап не считается реализованным, пока восстановление не проверено в тестовой среде. Данные клиента должны быть переносимыми и не привязанными к одному поставщику инфраструктуры.

## Чего не делать без отдельного решения
Не добавлять языки, не добавлять языки сверх 12 без списка от владельца (автоперевод 24 языков EXPORT ждёт списка), не писать персональные и закрытые данные в публичный блокчейн, не запускать необратимые миграции.

## Принятые решения
- Почта (задача 10a, решение владельца 2026-10-28): свой SMTP на бесплатном тарифе Brevo, только для регистрации: подтверждение аккаунта, сброс пароля, уведомление оператору о новой организации. Модуль `lib/mail.js` общий (nodemailer), учётные данные только в переменных окружения и в панели Supabase, пароль SMTP в чат и в код не попадает. Остальные письма позже. Лимит бесплатного плана 300 писем в день.
- План разработки ведётся в docs/ROADMAP.md. Добавлена задача 10a «Почта (SMTP)»: собственный SMTP для писем Supabase Auth (подтверждение, сброс пароля), письма приглашений и уведомлений через отправляющий модуль и таблицу очереди, SPF/DKIM/DMARC, подавление адресов после bounce. Встроенная почта Supabase для продакшена не годится. Секреты SMTP только в переменных окружения и панели Supabase.
- Приглашения сотрудников (миграция 0010): личная ссылка без отправки писем, в БД только хеш токена, срок 7 дней, принять может только аккаунт с той же почтой, лимит пользователей считает участников и открытые приглашения. В проде Confirm email включён обязательно. Активная организация выбирается кукой dpp_org, переключатель в боковой панели при членстве в нескольких организациях.
- Политика утверждения (решение владельца 2026-10-27, миграция 0009): при регистрации выбирается «составитель и утверждающий один человек» (одно ФИО ответственного) или «разные» (два ФИО, они должны различаться). В режиме «разные» аккаунт, который создал паспорт или отправил его на утверждение, утвердить его не может (БД: can_approve_passport, код: canApprove в lib/org-policy.mjs). Право passport.approve требуется всегда. ФИО это внутренние записи для документа об утверждении, на публичной странице не показываются, к аккаунтам пока не привязаны. Меняется только через set_approval_policy с записью в журнал. Для режима «разные» нужны приглашения второго пользователя, без них утвердить нельзя.
- Задача 9 (мастер паспорта): черновик создаётся функцией create_passport() с проверкой тарифа и месячной квоты (сначала лимит тарифа, потом докупленные кредиты; удалённые черновики квоту не возвращают). Шаги: 1 основное (товар и код партии), 2 состав и материалы, 3 этапы и документы, 4 проверка (ошибки блокируют, предупреждения и рекомендации нет), 5 итог и отправка на утверждение. Правила проверок в `lib/passport/checks.mjs`, они же перезапускаются на сервере при отправке. Состав считается «заявленным», пока к его партии или материалу не привязан проверенный документ с действующим сроком. Утверждение и публикация только в задаче 10, статусы approved/published пока невозможны (запрет в триггере БД). Для BASE шаг 2 содержит отдельный блок автозаполнения (ИИ/Excel), он пока заглушка и будет отдельной задачей. Проверки не означают юридического соответствия.
- Задача 8 (документы): личный закрытый бакет Storage, загрузка по подписанной ссылке, после загрузки сервер проверяет реальное содержимое файла (сигнатуры, макросы Office), считает SHA-256, версии не перезаписываются, скачивание только через проверку прав, новая версия сбрасывает статус проверки. Антивирусной проверки нет, это ограничение.
- Задача 8а: тарифы v2, дополнения, скидка UA2026, страна компании (миграции 0006 и 0007). Правило «PDF/blockchain/Verified»: плашка Verified и blockchain-статус только после утверждения человеком и подтверждённой транзакции.
- Бэклог владельца (Trust Page, конструктор полей, портал поставщика, аналитика QR) описан в docs/BACKLOG.md. Файлы поставщика через портал попадают во входящие на проверку человеком, а не напрямую в черновик.
- Задача 7 (поставщики, площадки, материалы, партии) сделана на общем конфигурируемом CRUD: описание сущностей в `lib/crud/entities.mjs`, общие страницы в `components/crud/`, общие действия в `lib/crud/`. Новые простые справочники добавляем описанием, а не копированием кода. Лимит поставщиков по тарифу проверяется и в коде, и в RLS (миграция 0005). Происхождение партии по умолчанию «заявление поставщика»; «проверено» ставит человек, «подтверждено документом» появится вместе с документами (задача 8).
- Лимиты паспортов платных тарифов подтверждены: в месяц. Задача 6 (товары и коллекции) сделана: миграция 0004, мягкое удаление, право чтения passport.read, правки passport.edit плюс функция manual_entry. Вкладки «Паспорта / Товары / Коллекции» внутри раздела «Товары и паспорта». Проверка данных в `lib/validation.mjs`, тесты `npm test`.
- Тарифы (задачи 5 и 5а): цены, функции и лимиты хранятся в БД (plans, plan_features, plan_limits, organization_subscriptions, addon_packs, organization_credits; миграции 0002 и 0003). Лимит паспортов на платных тарифах считается за календарный месяц (предположение, подтвердить), на FREE всего; докупленные паспорта не сгорают. «PDF-паспорт» в LITE понимается как внутренний PDF; публичный PDF на Trust Page разрешён владельцем отдельным шаблоном. Проверка на сервере: `requireFeature()` и `assertWithinLimit()` из `lib/auth/permissions.js` в каждом действии, зависящем от тарифа; для новых ограниченных таблиц в RLS использовать `within_limit()` и `has_feature()`. Превышение лимита блокирует только создание новых записей, существующие данные и опубликованные паспорта не трогаются. Смена тарифа вручную через SQL, пока оплата не подключена. Лимиты в миграции стартовые, их задаёт владелец продукта.
- Язык разработки русский: интерфейс сейчас показывается на русском (`lib/i18n/ru.js`), новые ключи добавляются сначала в ru. Базовый язык платформы английский (`en.js`, он же fallback), его дописываем перед задачей переводов. 12 языков из ТЗ переводятся отдельной последней задачей, до неё другие языки не трогать.
- Регистрация: имя обязательное (2–120 символов), компания необязательная. Без названия организация получает название «Моя организация», его можно изменить в Настройки → Организация.
- Дизайн-эталон: `docs/design/mockup.png` (14 экранов). Повторяй структуру экранов. Имена, цифры и фото из макета демонстрационные и в код не переносятся.
- Прежние названия Start/Professional/Enterprise и цены €99/199/399 из макета заменены сеткой выше.
- Стек пока: Next.js 14, JavaScript, Tailwind. Переход на TypeScript и Supabase решается на задаче 4 (БД и авторизация), не раньше.
- Долг MVP: форма `app/(app)/passports/new` с захардкоженным итальянским текстом и имитацией оплаты («Paga»). Оплату не развивать: заменить честным статусом, когда дойдём до тарифов. Строки перенести в i18n.
- Решение по стеку: Supabase (Auth, Postgres, RLS) принято, TypeScript откладывается. Задача 4 (БД, авторизация, организации, роли) написана, но не запущена против реального проекта: миграцию и сборку проверяет человек по docs/backend-setup.md.
- Задача 3 (каркас) выполнена: оболочка, 7 разделов, общие компоненты, i18n-обёртка (только EN), страницы 404/500, `.env.example`. Не проверена сборкой, первым делом запусти `npm install && npm run build`.
